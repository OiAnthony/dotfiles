# 中文技术文章写作

## 目标与默认读者

把复杂的软件工程内容写成同行愿意读、入门开发者能跟上、资深开发者可以检验的中文技术文章。

默认作者和读者均为 Web 软件从业者。大多数读者处于入门到中级阶段，少数在相关领域比作者更专业。写作同时守住两条线：

- 补齐理解主线必需的概念、机制和例子。
- 保留准确术语、事实边界、例外与适用条件。

作者是有实践经验的同行，不是全知导师，也不是品牌宣传者。不能用错误简化换取“易懂”。

## 使用边界

适用于技术原理、架构解释、方案比较、观点分析、教程、实践或故障复盘、内部培训、调查报告，以及对已有技术文章的重组、去重和严谨性编辑。

不用于 API reference、字段字典、release notes、PR、代码注释和短文案。主要依赖个人情绪和故事张力的公众号文章使用 `article-writer`。理解、判断、学习或实施是主要目标时，优先使用本 skill。

## 一、先确定写作契约

在内部明确，不机械输出：

1. **读者**：岗位、已有知识和最可能卡住的概念。
2. **场景**：扫读、查问题、系统学习、方案评审或内部分享。
3. **目标**：理解机制、做出判断或完成动作。
4. **主型**：解释、教程、比较、观点、复盘或调查。

一篇文章只有一个主导任务。背景、步骤、API 清单和观点论证不能无边界混合。

新增长文缺少事实材料或稳定提纲时，先给简洁的写作契约和带来源提纲。用户明确要求直接出稿，或已经提供稳定提纲时，直接写。编辑任务范围清楚时，不重复确认。

## 二、按文章类型组织

### 解释和教学

默认采用“先有体感，再讲机制，最后落到实操”：

1. 用开发者熟悉的真实场景说明问题。
2. 建立最小但完整的心智模型。
3. 用代码、流程、输入输出或反例解释机制。
4. 给出实践建议、适用边界和常见错误。

若读者已经知道问题，可以直接从结论或机制开始。不要把默认路径写成固定模板。

### 方案比较

1. 说明决策问题和评价维度。
2. 在同一维度比较，不做错位比较。
3. 区分事实、实验结果、判断和未知项。
4. 写出各方案成立的前提与失败条件。
5. 给出适用范围明确的结论和最小验证动作。

没有真实数据时，给出默认选择、风险和验证计划；不得虚构测试结果。待验证因素必须标为假设，不能暗示它天然有利于某方案。

### 技术观点和批判

先准确复述对方最强主张，再检查概念替换、局部优化冒充系统重构、相关性冒充因果、单例外推和产品宣称冒充验证结果。批判论证和系统行为，不猜测个人动机。

### 实践或故障复盘

分开时间线与解释线。时间线说明发生了什么；解释线说明根因、验证、修复和预防。按读者理解根因的顺序重组，不按作者调查顺序倾倒材料。

## 三、为入门读者搭桥

解释新概念时按需执行：

1. 用熟悉对象建立锚点。
2. 给出准确术语和最小定义。
3. 说明它在当前问题中的作用。
4. 紧跟具体例子、输入输出或反例。
5. 再说明例外和权衡。

只解释理解主线必需的概念。类比之后指出成立和失效的边界，不能用类比替代机制。代码示例必须语义完整；未定义函数要说明职责，涉及密钥和运行时时要区分“服务端可访问”与“可以安全返回给客户端”。

用户故事至少包含场景、输入、系统行为、风险、预期行为和小结。它用于让风险可判断，不用于煽情。

## 四、控制结构与信息预算

- 内容型标题必须传递结论或问题，避免“背景”“问题分析”“更多思考”等空标题。
- 结论、关键词和限制条件前置。
- 只看标题、每节首句和图表标题，应能复述主线。
- 并列项用项目符号；有依赖的步骤用编号；同维度比较用表格；只有图比文字更快建立关系时才使用 Mermaid。
- 图表必须降低理解成本，由正文引入并说明观察重点，不能复制正文。

### 视情况使用 Mermaid

先明确图要回答的问题。若一小段文字、列表或表格已经足够清楚，不画图。适合使用 Mermaid 的场景：

- **flowchart**：有分支的流程、数据流、决策路径，或少量组件之间的静态关系。
- **sequenceDiagram**：请求链路、协议交互、异步消息和带时间顺序的跨组件调用。
- **stateDiagram-v2**：生命周期、有限状态及合法或非法转换。
- **erDiagram**：实体关系和基数；只保留解释问题所需的属性。
- **classDiagram**：类型、接口、继承和组合关系确实是论点核心时使用。

不要为了“有图”而画装饰图。一个图只表达一个主要结论；节点、参与者或分支过多时，按读者问题拆图。标签使用短而具体的业务名称，连线标明动作、数据或触发条件，方向在同一篇文章内保持一致。

同一问题默认只选一种图。参与者和主要路径相同时，不要同时绘制 flowchart 与 sequenceDiagram：时间顺序和跨组件交互是重点时选 sequenceDiagram；分支、决策或数据去向是重点时选 flowchart。只有第二张图回答不同问题并提供第一张图没有的信息时，才能同时保留。

图前用一句话说明它回答什么问题；图后只指出阅读顺序、关键路径、异常分支或最容易误解的关系。图用于替代一段难懂的文字，不是附加装饰；加入图后删除重复的 ASCII 流程、逐步复述和同义列表。正文仍须保留关键结论与限制，不能让核心信息只存在于图中。

Mermaid 输出还必须满足：

- 优先使用目标平台广泛支持的稳定语法。Mermaid C4 仍是实验语法，`architecture-beta` 依赖较新版本；未确认渲染器版本时，优先使用 `flowchart`、`sequenceDiagram` 或 `stateDiagram-v2`。
- 在渲染器支持时添加 `accTitle` 和 `accDescr`；无论是否支持，都在正文提供等价的文字说明。
- 在目标平台或兼容版本中实际渲染，检查语法、节点重叠、标签截断、方向和移动端可读性。无法渲染时明确标注“Mermaid 未验证”，不能声称图已验证；同时提供文字回退。
- 图中的组件、调用和状态同样受事实边界约束。不得为了让图闭合而补造未知链路、返回值或状态转换。

严格遵守用户指定的篇幅，目标字数允许约 ±15% 浮动。用户没有指定长度时，使用完成任务所需的最短篇幅。超出上限时，先删除次要章节、重复结论和第二个同类例子，再压缩措辞。

## 五、让行文流畅

- 按读者的思考或操作顺序组织，不按资料收集顺序组织。
- 每段只完成一个任务：提出主旨、解释机制、提供证据、举例或收束。
- 首句说明主旨，或明确与上文的因果、转折、递进、对照或回指。
- 新概念紧跟定义或例子，不让问题长期悬置。
- 流程说明与观点论证分开；后文引用前文，不重复整套流程。
- 明确主体、动作和对象；条件先于动作，动作先于结果。
- 一个句子只承载一个主要结论；一个概念只使用一个术语。

中文句法保持完整。API、代码标识符、配置键、协议和产品名保留原文并使用反引号。有稳定译名时使用中文；没有时首次写“中文名称（English term）”，后文统一名称。

语言直白、具体、有判断，但不强制俚语、口头禅、情绪标点、自嘲或“一句话一段”。不使用固定开头、固定尾部和固定字数。

## 六、守住事实和证据边界

内部区分：已观察事实、一手来源陈述、独立证据、作者推断、未知项和适用范围。

优先使用源码、官方文档、标准、论文、运行结果和可复现实验。厂商宣传只能证明厂商如何描述产品，不能单独证明效果。来源矛盾时并列呈现，不静默选择有利一方。引用放在它支撑的结论附近。

用户明确给出的“已知边界”是封闭证据集：

- 不把相邻但未提供的能力、入口、流程或结果补写成事实。
- “未看到”不等于“不存在”；“缺少清晰可验证的入口”不等于“没有任何人工处理办法”。
- 未验证流程使用条件句，不能写进确定性时序。
- 需要更强结论时，明确缺少什么源码、日志、产品文档或实验，不用顺滑措辞填补证据缺口。

## 七、编辑已有文章

默认做最小充分修改，保留宏观大纲、核心观点、事实边界和真实经历。允许重写标题、调整章节内部顺序、合并重复命题、用交叉引用替代重复机制、分开事实与推断，并收紧超出证据的结论。

不要因为编辑而新增原文未提出的风险、产品能力或评价维度。除非用户要求扩写，修改稿不应明显长于原稿；优先删除重复，再补必要解释。

## 八、默认交付 Markdown 文件

文章、改稿、提纲、审稿报告及其他实质性成果，默认写入 Markdown 文件，而不是只在聊天中粘贴全文。这样便于继续编辑、版本管理和发布。

1. 用户指定路径或文件名时，严格使用该位置。
2. 用户未指定时，在当前工作目录创建 `.md` 文件，文件名取自文章标题，去除文件系统不安全字符；例如 `OAuth2.0-认证逻辑.md`。
3. 写入前检查目标是否已存在。用户未明确要求覆盖时，不覆盖现有文件；使用语义清晰的递增后缀，如 `-2`。
4. 文件必须包含完整标题和正文，不加入写作过程、自评分、反馈标记或无关说明。
5. 聊天回复只报告文件路径、内容范围和必要的证据或未验证项，不重复粘贴全文。
6. 用户明确要求“直接在聊天中输出”“不要创建文件”或指定其他格式时，以用户要求为准。
7. 只有极短的事实回答、写作契约确认或澄清问题可以直接在聊天中返回；它们不属于文章交付物。

## 九、三遍验收

### 结构与证据

检查读者任务、章节顺序、类型混杂、重复内容，以及强结论的证据、前提和适用范围。

### 可读性

检查标题与首句、段落单一任务、主体动作、术语指代、列表平行性，以及抽象概念后的具体例子。

### 真实阅读与文件检查

1. 扫读标题、首句、列表和图表，确认能够复述主线。
2. 线性通读，逐节问“为什么现在讲这个”，删除需要回读、突然跳转或重复论证的部分。
3. 检查错字、病句、断链、代码围栏、Markdown 标题层级和列表缩进。
4. 确认最终文件存在、扩展名为 `.md`、内容完整且未意外覆盖旧稿。

教程步骤在环境允许时必须实际执行，并核对预期结果和失败信号。无法执行时，明确标注“未验证”，不能声称已执行或编造结果。技术比较检查评价维度一致。批判文章检查对方主张是否被准确复述。

这些检查只指导修改，不输出成冗长自评分。

## 输出规则

- 用户要文章或改稿时，交付完整 Markdown 文件。
- 用户要提纲时，每节说明读者问题、核心结论、证据需求和前后关系，并交付 Markdown 文件。
- 用户要审稿时，先报告最影响理解和正确性的结构、事实、逻辑问题，再谈措辞，并交付 Markdown 文件。
- 用户要改稿时，直接给修改稿，并在聊天中简述保留、重组和删除的内容。
- 不编造第一人称经历、来源、数据、测试结果或专家共识。
- 默认使用简体中文；代码、标识符、协议和产品名保持原文。

最终标准：入门读者能够建立正确心智模型，专业同行能够检查论证和边界。两者冲突时，修正解释路径，不牺牲技术事实。
